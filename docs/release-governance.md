# 发布治理

本项目区分“功能完成、候选验证、公开发布、线上部署”四种状态。任何单项测试、提交或镜像构建通过，都不自动授权进入下一状态。

## `x.y.0` 用户价值门槛

新的次版本必须同时满足：

1. 面向明确的首要用户，形成至少一条从入口到结果与导出的完整用户闭环。
2. 发布说明能用不超过五条重点说明用户获得了什么；只有内部重构、测试补强或发布工程变化时，优先进入补丁版本。
3. 数值、图形、证据、异常路径和回滚均有可复核验收，不用访问量替代正确性。
4. 明确列出非目标，不借次版本引入账号、商业平台或新的结构分析域。

## 节奏与确认

- 相邻稳定版本之间默认保留不少于 24 小时的候选观察窗口；修复安全或发布阻断问题可走补丁版本。
- 同一天不得连续发布两个稳定次版本。一次性撤回和合并纠偏必须由维护者明确确认，并保留重写前证据。
- 创建或移动稳定 Tag、发布 GitHub Release、推送正式镜像和更新线上环境，均需要维护者明确说出要发布的版本号。
- 候选观察期只处理 P0/P1 缺陷、证据缺口和发布阻断项，不用继续堆功能证明版本“更大”。

## 不可变与回滚

正常发布后的 Tag、Release 资产、`SHA256SUMS` 和镜像 digest 不得改写。若在公开推广前进行一次性发布线纠偏，必须先验证替代制品，再撤下旧 Release，并记录原提交、摘要、发布时间和回滚镜像。
